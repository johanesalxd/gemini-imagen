## 5. ISSUES AND INCONSISTENCIES

ISSUE 1 (Minor — functional deviation):
  candidate_count vs number_of_images for multi-image requests.
  The plan spec shows number_of_images in ImageConfig. The implementation uses
  candidate_count in GenerateContentConfig. For single-image (the smoke test),
  this doesn't matter. For --count > 1, behavior depends on which parameter
  the API actually processes. Risk: --count 4 may only return 1 image if the API
  ignores candidate_count and expects number_of_images instead.

ISSUE 2 (Cosmetic — minor style drift from plan):
  In the plan's generate(), image_config_kwargs is initialized as:
    image_config_kwargs = {"number_of_images": count, "aspect_ratio": aspect_ratio}
  
  In the implementation:
    image_config_kwargs: dict = {"aspect_ratio": aspect_ratio}
  
  The dict type annotation (dict without subscript) is fine for Python 3.13.
  The count field is moved to candidate_count. See ISSUE 1.

ISSUE 3 (Cosmetic — formatting):
  The plan's Python code uses i+1 without spaces in the f-string filename.
  The implementation uses i + 1 with spaces. Both are valid; ruff prefers spaces.
  This is a cosmetic difference only.

ISSUE 4 (Informational):
  The smoke test produced a JPEG file, not PNG. The code correctly handles
  dynamic mime type extraction ("image/jpeg" -> ext "jpeg"). This is expected
  API behavior and not a bug — it confirms the mime type branch in the code works.

ISSUE 5 (Informational — .mise.toml is empty):
  .mise.toml is 0 bytes. This is intentional per the plan ("empty file — required
  to prevent mise shim errors"). No tools are configured in mise for this project.
  Users must run "mise exec -- uv run imagen.py" as shown in README, which works
  because mise will find uv from the ambient environment.

NO SECURITY ISSUES FOUND:

  - GOOGLE_API_KEY read from environment or file, not committed
